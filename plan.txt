OrderFlow — Distributed Food Delivery Platform

1. Project Overview

OrderFlow is a full-stack food delivery web application inspired by platforms such as Deliveroo and Uber Eats.

The project allows customers to browse restaurants, order food, and track their order status in real time. Restaurants can receive and manage orders, while drivers can accept deliveries and update delivery progress.

The main purpose of the project is not simply to build another food-ordering website. The backend will use a distributed, event-driven architecture to demonstrate software engineering concepts such as microservices, message queues, asynchronous communication, concurrency, failure recovery, retries, idempotency, and real-time communication.

The final project should therefore demonstrate both:

1. A polished, understandable web application.
2. A technically interesting distributed backend system.

2. Main Users

Customer

Customers should be able to:

* Browse restaurants.
* View restaurant menus.
* Add food to a basket.
* Place an order.
* View their previous/current orders.
* Track the current order status.
* Receive real-time status updates.

Example order status:

Order confirmed → Restaurant accepted → Preparing → Driver assigned → Ready → Picked up → On the way → Delivered

Restaurant

Restaurants should be able to:

* View incoming orders.
* Accept or reject an order.
* Mark an order as preparing.
* Mark an order as ready for collection.
* View active orders.

Driver

Drivers should be able to:

* View available delivery jobs.
* Accept a delivery.
* View pickup and delivery information.
* Mark an order as picked up.
* Mark an order as delivered.

3. Example User Flow

A customer opens the website and selects a restaurant.

The customer chooses food and adds it to their basket.

For example:

2 × Chicken Burger
1 × Fries
1 × Coke

The customer places the order.

The Order Service creates the order with a status such as:

PENDING

The system publishes an OrderCreated event.

The Restaurant Service receives the event and displays the new order to the restaurant.

The restaurant accepts the order.

The system publishes a RestaurantAccepted event.

The order status changes to:

PREPARING

The Delivery Service creates a delivery request.

A driver accepts the delivery.

The system publishes a DriverAssigned event.

The restaurant finishes preparing the food and marks it as ready.

The driver collects the food.

The status becomes:

PICKED_UP

The driver delivers the food.

The final status becomes:

DELIVERED

Throughout this process, the customer’s browser receives real-time updates.

6. Why Use Distributed Architecture?

A simple version of this application could use:

React → FastAPI → PostgreSQL

However, that would mostly demonstrate normal full-stack CRUD development.

OrderFlow instead separates important responsibilities into independent services.

For example:

The Order Service manages orders.

The Restaurant Service manages restaurant operations.

The Delivery Service manages drivers and deliveries.

Instead of directly calling every other service, services can communicate through events using RabbitMQ.

This creates realistic distributed-system problems that the project can solve.

8. Distributed Systems Concepts

The project should demonstrate several important distributed-systems concepts.

Message Queues

RabbitMQ will allow services to communicate asynchronously.

A service does not always need to wait for another service to finish its work.

Failure Recovery

Services should be able to temporarily fail without destroying the entire order process.

Example:

The Order Service publishes an OrderCreated event.

The Delivery Service is temporarily unavailable.

The message should not simply disappear.

RabbitMQ keeps or requeues the message.

When the Delivery Service becomes available again, it processes the pending message.

Retries

Some operations may temporarily fail.

The system should retry appropriate operations instead of immediately marking them as permanently failed.

A retry limit should prevent infinite retry loops.

Dead-Letter Queue

Messages that repeatedly fail should eventually be moved to a dead-letter queue.

This prevents broken messages from continuously blocking or disrupting normal processing.

Idempotency

Message brokers can sometimes deliver the same message more than once.

For example:

OrderCreated #9281

OrderCreated #9281

The Delivery Service must not accidentally create two deliveries.

Consumers should therefore be idempotent.

Before processing an event, the service can check whether that event has already been processed.

Eventual Consistency

Different services may not contain exactly the same state at exactly the same moment.

For example, the Order Service may know that a restaurant accepted an order slightly before the Delivery Service receives the corresponding event.

The project can demonstrate how distributed systems handle this temporary inconsistency.

Concurrency

Multiple customers may place orders simultaneously.

Multiple drivers may also attempt to accept the same delivery.

The system must prevent race conditions such as two drivers being assigned to one delivery.

Horizontal Scaling

Multiple worker instances can process messages.

For example:

Worker 1
Worker 2
Worker 3

Jobs/events can be distributed between them.

This demonstrates how additional workers can increase processing capacity.

9. Real-Time Order Tracking

Customers should not need to refresh the page repeatedly.

The backend should push status changes to the frontend using WebSockets or Server-Sent Events.

For example:

Order confirmed ✓

Restaurant accepted ✓

Preparing ✓

Driver assigned ✓

Picked up

Delivered

When the restaurant or driver changes the order status, the customer’s page should update automatically.

10. Failure Demonstration

One of the most important parts of the project should be demonstrating that the distributed architecture actually works.

Example experiment:

1. Start the complete system.
2. Place an order.
3. Stop the Delivery Service.
4. Let the restaurant accept the order.
5. The DeliveryRequested event cannot currently be processed.
6. Restart the Delivery Service.
7. The pending event is processed.
8. A delivery is created successfully.
9. The customer’s order continues normally.

Another experiment could deliberately send the same event twice.

The system should prove that idempotency prevents duplicate deliveries.

These demonstrations make the distributed-systems features visible rather than simply claiming that the project uses microservices.

12. What Not to Build

The project should remain manageable.

It does not need:

* Real payment processing.
* Real restaurants.
* Real drivers.
* A real delivery business.
* Advanced GPS tracking.
* A mobile application.
* Complex recommendation algorithms.
* Ten or more microservices.
* Kubernetes at the beginning.

Driver movement can be simulated.

Restaurant/menu data can also be seeded.

The technical depth of the backend is more important than recreating every feature of Deliveroo.

16. Main Project Goal

The goal is not to build a complete Deliveroo clone.

The goal is to build a realistic food-delivery product that provides an understandable interface for demonstrating deeper backend engineering.

A recruiter should be able to open the project and immediately understand:

“This is a working food-delivery application.”

A software engineer should be able to examine the architecture and see:

“This student understands APIs, messaging, asynchronous systems, service failures, retries, concurrency, idempotency, and distributed-system design.”

The project should therefore prioritise technical depth, reliability, and clear demonstration over having a very large number of features.
